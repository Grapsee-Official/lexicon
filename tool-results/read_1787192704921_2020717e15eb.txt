  1432→Design notes:
  1433→- Chose `#import` over `#include` because both the umbrella header and the bridging header are processed by Clang in Objective-C / module-aware mode (the only mode that applies for Swift interop). `#import` gives built-in include-guard semantics, and `c_api.h`'s `#pragma once` makes the combination idempotent.
  1434→- Chose `umbrella header` over individual `header "..."` directives in the module map so that any future additions to `LexoraEngine.h` (e.g. wrapping more C++ ABI headers, versioning macros) are automatically re-exported without touching `module.modulemap`.
  1435→- Kept the `link "LexoraEngine"` directive as a hint, even though the iOS app target will likely link `LexoraEngine.framework` explicitly via Xcode's "Link Binary With Libraries" build phase. The `link` directive is a no-op when the framework is already linked and helps `clang -emit-module` users who build via the command line.
  1436→- Did NOT switch to a framework-style `framework module LexoraEngine { ... }` module map because the iOS app target treats the C++ engine as an embedded static framework produced by CMake (`-DBUILD_SHARED_LIBS=OFF` per `cmake/Toolchain-iOS.cmake`), not as a true Clang `.framework` resource bundle. A non-framework `module` declaration is the right level of abstraction here.
  1437→- The `../../cpp/include/lexora/c_api.h` path is intentionally identical in both the umbrella header and the bridging header. They are NOT mutually exclusive: the bridging header is the legacy Swift-interop path (set `SWIFT_OBJC_BRIDGING_HEADER` and you're done), while the module map + umbrella header is the modern path (`import LexoraEngine` works without any bridging header). Both can coexist; users can pick whichever they prefer.
